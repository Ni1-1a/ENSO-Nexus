# От промтов к агентам со скилами

**Что это за документ.** Первая половина — схема платформы: как она устроена
сегодня, что за что отвечает, до каждого файла. Вторая — предложение перейти
к агентской структуре и порядок такого перехода.

**Состояние на 10.09.2026.** Платформа работает на двух доменах, в ней шесть
рабочих модулей, 590 тестов, 114 файлов сервера и 430 промтов в библиотеке.
Агентской структуры сейчас нет, и этот документ объясняет, почему её стоит
завести и как это сделать, ничего не сломав.

---

# Часть I. Схема устройства

Схема разложена на три уровня. Первый читается за минуту, третий нужен, когда
правишь код. Смотреть подряд не обязательно — уровни независимы.

| Уровень | Что показывает | Сколько строк |
|---|---|---|
| 1 | Пять слоёв платформы и связи между ними | 5 |
| 2 | Папки внутри каждого слоя | 24 |
| 3 | Каждый файл и его ответственность | 320 |

## Уровень 1 — пять слоёв

```
┌─────────────────────────────────────────────────────────────┐
│  1. ВХОД И ПРОЕКТЫ                                          │
│     Кто работает и над чем. Проект — единица работы,        │
│     внутри него живут все модули.                           │
├─────────────────────────────────────────────────────────────┤
│  2. МОДУЛИ                                                  │
│     Шесть рабочих + датасет + витрина. Каждый — свой         │
│     экран, свой роутер, свои таблицы.                       │
├─────────────────────────────────────────────────────────────┤
│  3. ДВИЖОК                                                  │
│     Чем делают: обращения к моделям, геометрия участка,      │
│     разбор и сборка документов, выгрузки.                   │
├─────────────────────────────────────────────────────────────┤
│  4. ЗНАНИЯ                                                  │
│     На чём основано: тексты промтов, библиотека ролей,       │
│     реестр НТД, правила нормоконтроля.                      │
├─────────────────────────────────────────────────────────────┤
│  5. ДАННЫЕ И ЭКСПЛУАТАЦИЯ                                   │
│     Где лежит и как живёт: базы, файлы, тесты, деплой.       │
└─────────────────────────────────────────────────────────────┘
```

Правило, которое держит всю конструкцию и объясняет её форму:

> **Модель отвечает за интерпретацию и планирование. Детерминированный код
> отвечает за координаты, площади, пересечения, буферы и финальную инженерную
> геометрию.**

Поэтому слой 3 толще слоя 4: модель формулирует правило «охранная зона 10 м от
оси объекта», а буфер строит движок, и результат воспроизводится до
миллиметра.

## Три сквозных маршрута

Схема оживает, когда видно, как запрос проходит слои насквозь.

**Посадка здания.** Чертёж и ГПЗУ ложатся в `data/uploads` → `cad-geometry`
превращает DWG в объекты в метрах → `restriction-extract` просит модель
сформулировать правила ограничений (без единой координаты) →
`restriction-engine` строит зоны буферами → `placement-engine` перебирает
пятна, `grid-shape` даёт контур по сетке колонн → `variants` отбирает четыре
разных → человек выбирает → `report` и `drawing` собирают комплект.

**Анализ ТЗ.** Текст задания → три структурных прохода
(`tz-classify` → `tz-completeness` → `tz-findings`) → дальше только код:
матрица полноты по чек-листу, дедупликация, вердикт → человек принимает
решения → `tz-suggest` даёт три формулировки на замечание → `revision`
собирает исправленную редакцию → выгрузка DOCX.

**Проверка документа.** Загрузка сама запускает прогон → тип определяется
маркерами кода, при неоднозначности моделью, выбор человека сильнее →
`doclib.ROUTES` находит профильный промт библиотеки → прогон → перечень
ссылок на НТД строится кодом в каждом прогоне и сверяется с реестром.

Во всех трёх маршрутах модель работает ровно там, где нужен смысл, и нигде —
там, где нужно число.

# Часть II. Где здесь промты сегодня

### Одна таблица, которая объясняет всю текущую модель

В коде 45 обращений к промтам, за ними 34 имени и 35 файлов в `prompts/`.
Каждое обращение — это заранее написанная пара «место в коде → имя промта»:

| Кто зовёт | Какой промт | Когда |
|---|---|---|
| `services/pipeline.js` | `tasks/analysis-run` | запуск анализа исходных данных |
| `services/tz/analyze.js` | `tz-classify`, `tz-completeness`, `tz-findings`, `tz-suggest` | три прохода проверки ТЗ и предложения формулировок |
| `services/doccheck/analyze.js` | `doccheck-classify`, `doccheck-run` | определение типа документа и профильная проверка |
| `services/geometry/restriction-extract.js` | `restriction-extract` + три повтора-задания | извлечение ограничений из документов |
| `services/normo/checks/llm.js` | `normo-check` | проверка версии раздела по правилам |
| `services/claude/adversary.js` | `adversary-review`, `adversary-rewrite` | проверяющий перед отправкой ответа |
| ещё 12 мест | ещё 20 имён | конспекты, распознавание, чат, офис, датасет |

Правило здесь одно и оно жёсткое: **решает код, а не задача**. Промт не
выбирается — он вписан в вызов. Поэтому новый вид документа означает правку
кода, а не пополнение библиотеки.

### Два хранилища знаний, которые почти не встречаются

| | `prompts/` | `библиотека-промптов/` |
|---|---|---|
| Файлов | 35 | 430 промтов, 12 ролей |
| Кто читает | сервер, в каждом прогоне | человек, глазами |
| Кто выбирает | код | человек |
| Формат | голый текст промта | пост канала + пособие |
| Связь с кодом | прямая, по имени | карта на 14 типов документа |

Мост между ними — карта `doclib.ROUTES` в модуле «Проверка документа».
Она устроена сложнее, чем кажется: у каждого из четырнадцати типов документа
записан **каркас роли** (`systemId`), **умолчание** (`promptId`) и **список
альтернатив**, которые человек может взять вместо умолчания. Всего через неё
достижимы 69 промтов библиотеки — 16 % её объёма. Остальные 361 платформа не
открывает никогда.

### Хорошая новость: библиотека уже наполовину машиночитаема

У всех 430 файлов библиотеки одинаковый и полностью заполненный фронтматтер —
девять полей без пропусков:

| Поле | Что в нём | Годится для автоматики |
|---|---|---|
| `role` | одна из 12 ролей (ГИП, сметчик, ПТО, АР, КЖ/КМ…) | да, это готовый ключ скила |
| `section` | шифр или тема: `АР`, `КР`, `ПЗУ`, `ОВ+ВК`, `сметы`, `акты` | да, прямой ключ «документ → пакет» |
| `kind` | глубина: полный (136), сверка (136), быстрый (86), запрос (54) | да, как фильтр |
| `task`, `inputs` | что делает и что подать на вход | читается человеком, свободный текст |
| `id`, `title`, `source_file`, `source_post` | опознание и происхождение | да, для трассировки |

Чего в описи НЕТ и что придётся добавить:

- **пометки контура.** Правило «необезличенные данные — только локально»
  записано прозой в этом самом документе; поля во фронтматтере нет ни у
  одного файла;
- **ссылок на НТД отдельным полем.** Шифры нормативов встречаются в телах
  74 файлов из 430, но выковыривать их регулярками — не опись;
- **версий.** Ни поля версии, ни даты правки: понять, какой промт свежее,
  нельзя.

Это и есть объём первого этапа: не переписывать 430 текстов, а дописать три
поля. `manifest.tsv`, вопреки названию, описью промтов не является — это
перечень 81 вложения канала с привязкой к посту.

### Что уже похоже на агента

Три места работают почти по агентской схеме, и это готовые семена:

1. **Проверяющий перед отправкой** (`claude/adversary.js`). Черновик ответа
   уходит той же модели с ролью критика; вердикт «revise» возвращает ответ
   автору на одну доработку. Это отдельная роль со своим промтом и своим
   правом остановить результат.
2. **Автоподбор промта по документу** (`doccheck/analyze.js`). Тип документа
   определяется маркерами кода, при неоднозначности — моделью, а выбор
   человека сильнее любой догадки. Это выбор инструмента под задачу.
3. **Обсуждение фрагмента** (`services/fragment-chat.js`). Модель получает не
   голый текст, а собранное место: модуль, проект, подпись, окружение. Это
   сборка контекста под вопрос.

Чего у всех трёх нет: они не умеют брать другой инструмент, если первый не
подошёл, и не оставляют следа «почему выбрано это».

# Часть III. Что мешает — пять ограничений с доказательствами

### 1. Контекст переполняется, потому что грузится всё сразу

Боевой прогон 09.09.2026: промт вырос до 130 тысяч знаков при окне 71 936
токенов. Ответу оставалось около трёх тысяч, думающая модель обрывалась на
середине JSON, платформа переспрашивала «короче» — двенадцать вызовов по шесть
минут, и после каждого в ленту падала одна и та же карточка. Тринадцать
карточек за полтора часа.

Починено обрезкой: документы укладываются в остаток заранее, думающей модели
гарантируется пятая часть окна под ответ. Но причина осталась — **в промт
кладётся всё, что может пригодиться, потому что решить, что именно нужно,
некому**.

### 2. Реестр скилов уже написан — от руки и внутри кода

Это самая важная находка разбора. `doclib.ROUTES` — не таблица соответствий,
а **реестр ролей в чистом виде**: каркас роли, действие по умолчанию, список
допустимых альтернатив. Ровно из этих трёх вещей и состоит скил.

| Что в `ROUTES` | Как это называется у скилов |
|---|---|
| `systemId` — каркас роли | тело скила |
| `promptId` — что взять по умолчанию | действие скила |
| `alternatives` — что ещё уместно | остальные действия того же скила |
| ключ `razdel-ar`, `razdel-kzh` | имя скила |

То есть агентская структура на платформе уже наполовину написана — но живёт
в коде, поддерживается руками и покрывает 69 промтов из 430. Каждый новый
тип документа означает правку файла и релиз. Перенести этот реестр из кода в
папки скилов — не переделка, а перенос.

### 3. Проверяющий один на все задачи

`adversary-review.md` — общий промт: противоречия фактам сессии, выдуманные
основания, уход от вопроса. У проверки сметы, проверки чертежа и проверки ТЗ
разные признаки вранья, но критик один и тот же. На слабой модели он ошибается
сам — это уже ловили и лечили ужесточением формулировок.

### 4. Трассировки «приём → промт → находка» нет

`нормоконтроль/prompts/README.md` требует, чтобы каждый промт перечислял в
шапке номера приёмов, которые он реализует. Это соглашение о ревью, а не
механизм: ничто не мешает написать промт без номеров, и ничто не покажет, из
какого приёма выросла конкретная находка в заключении.

### 5. Планируемые агенты остались планом

Семь агентов нормоконтроля (`extractor-rules`, `check-document`,
`check-cross-section`, `findings-writer`, `verifier`, `diff-impact`,
`ingest-vision`) расписаны с приёмами и статусом «Этап 3». Файлов промтов
для них нет. Причина не в лени: под них нет формы, в которой агент мог бы
жить, — только «ещё один промт в общей папке».

# Часть IV. Что такое скил и что такое агент

Слова заняты, поэтому договоримся о значениях прямо здесь.

**Скил** — папка с ролью, которую можно взять целиком. Внутри: описание
«когда меня брать», текст роли, машиночитаемый чек-лист, детерминированные
скрипты и образцы. Ключевое свойство — **описание читается всегда, тело
грузится по надобности**. Двенадцать скилов стоят в контексте столько же,
сколько абзац текста; открывается один — нужный.

**Агент** — исполнитель задачи, у которого есть: задача, список доступных
скилов, бюджет обращений и журнал. Он решает, какой скил взять и в каком
порядке, но **не решает, чему равно число**.

Разница с сегодняшним днём — в том, где живёт решение:

| | Сегодня | Агентская структура |
|---|---|---|
| Какой текст уйдёт модели | вписано в код | выбирает агент по описанию скила |
| Новый вид работы | правка кода + релиз | новая папка скила |
| Что попадает в контекст | всё, что собрал код | описания + одно открытое тело |
| Почему выбрано это | нигде | в журнале прогона |
| Кто считает площадь | код | код, и только код |

Последняя строка — граница, которую нельзя сдвигать. Правило платформы
действует без изменений: **модель отвечает за смысл и порядок, код отвечает
за координаты, площади, пересечения и реквизиты**.

# Часть V. Целевая картина

Четырнадцать таких папок уже описаны — в коде, полями `systemId`,
`promptId` и `alternatives`. Речь о переносе, а не о сочинении с нуля.

### Скил как папка

Возьмём не выдуманный пример, а существующий маршрут `razdel-ar` — тот
самый, что сегодня записан в коде:

```
skills/razdel-ar/
  SKILL.md          описание «когда брать» + каркас роли
                    (сегодня — systemId: proekt-ar-nk-karkas)
  actions/
    sostav-po-pp87.md      умолчание
                           (сегодня — promptId: proekt-ar-nk-06)
    01…15.md               остальные четырнадцать проверок
                           (сегодня — alternatives)
  checklist.yaml    те же проверки списком, машиночитаемо
  scripts/          детерминированные шаги: сверка состава, арифметика
  references/       выдержки НТД, шаблоны формулировок
  examples/         пары «вход → эталон» из модуля «Датасет»
```

Слева — папка, справа — то, чем это является в коде сегодня. Ни одного
нового текста писать не нужно: все шестнадцать промтов уже лежат в
библиотеке и уже достижимы платформой.

Строка `examples/` — не украшение. Модуль «Датасет» уже собирает пары
«вопрос → эталонный ответ», подтверждённые человеком. Сегодня они уходят в
файл для дообучения; в скиле они становятся образцами, которые модель видит
в работе.

### Шапка скила — единственное, что грузится всегда

```yaml
---
name: razdel-ar
description: >
  Нормоконтроль раздела АР: состав листов по ПП № 87, оформление по
  ГОСТ Р 21.101, повторяемость, сверки со смежными разделами. Брать, когда
  на входе лист или комплект АР. Не брать для КЖ, ОВ, ВК, смет.
действие_по_умолчанию: sostav-po-pp87
контур: local_only
разделы: [АР]
источники: [ГОСТ Р 21.101-2026, ГОСТ 21.002-2014, ПП РФ № 87]
версия: 1
---
```

Поле `description` — единственное, что модель видит всегда. Оно написано
так, чтобы отвечать на один вопрос: брать этот скил или не брать. Строка
«не брать для КЖ, ОВ, ВК, смет» здесь важнее всего остального: без неё
подбор путается на смежных разделах.

Поле `контур` — не формальность. В библиотеке уже размечено, какие промты
работают только в локальном контуре: спецжурналы, сметы с расценками,
комплекты ПД. Гейт домена и допуска в платформе есть
(`services/ai/cloud-access.js`), скилу остаётся объявить своё требование.

### Агент как исполнитель с границами

Шаг агента — это одно из трёх, и ничего больше:

| Шаг | Что делает | Кто исполняет |
|---|---|---|
| `взять скил` | открывает тело роли | реестр скилов |
| `позвать скрипт` | считает, сверяет, разбирает | детерминированный код |
| `записать находку` | формулирует замечание со ссылкой | модель |

Считать самому агенту запрещено схемой ответа: варианта «вычислить» в ней
нет. Это тот же приём, которым сегодня закрыт расчёт геометрии — модель
формулирует правило, буфер строит движок.

# Часть VI. Переход — четыре этапа

Каждый этап заканчивается проверяемым результатом. Без него следующий не
начинается: это правило проверки платформы, а не пожелание.

### Этап 1. Опись и обёртка

**Что делаем.** Двенадцать ролевых пакетов библиотеки превращаем в двенадцать
папок `skills/` с `SKILL.md`. Тексты не переписываем — переносим и снабжаем
шапкой. Во фронтматтер библиотеки дописываем три недостающих поля: `контур`,
`источники`, `версия`. Заводим `server/services/skills.js` по образцу
`prompts.js`: чтение, кэш по времени правки, внятная ошибка на пустой файл.

Опорой служит существующая опись: `role` и `section` уже заполнены у всех 430
файлов и дают готовое разбиение на скилы — придумывать его заново не нужно.

**Чего НЕ делаем.** Не трогаем ни один существующий вызов `prompts.load`.
Платформа работает как работала.

**Как проверяем.** Тест: у каждого скила заполнены `name`, `description`,
`контур`; все `разделы` есть в `нормоконтроль/knowledge/sections.yaml`; все
`источники` сверены с реестром НТД (208 записей). Живая проверка: прогон
«Проверки документа» на боевом комплекте даёт тот же результат, что и до.

**Срок.** Две недели. Риск низкий: ничего работающего не меняется.

### Этап 2. Подбор скила вместо жёсткой карты

**Что делаем.** Карту `doclib.ROUTES` не переписываем, а **выворачиваем
наружу**: то, что сейчас лежит в коде тремя полями, переезжает в шапку скила.
Каркас роли становится телом скила, умолчание и альтернативы — его
действиями. Код перестаёт хранить список и начинает его читать.

Дальше подбор идёт по описаниям: модель получает список строк-описаний и
документ, возвращает имя скила и уверенность. Маркеры кода остаются первыми:
ровно одно совпадение по маркеру — модель не зовётся вовсе.

**Правило, которое переносим без изменений.** Выбор человека сильнее любой
догадки. Оно уже работает в «Проверке документа» и обязано пережить переход.

**Как проверяем.** Двадцать боевых документов, размеченных вручную. Доля
верных подборов должна быть **не ниже** прежней карты. Хуже — этап
откатывается, карта остаётся.

**Срок.** Две недели.

### Этап 3. Агент с бюджетом и журналом

**Что делаем.** `server/services/agents/runtime.js`: задача, список скилов,
бюджет обращений, журнал шагов. Всё, на чём он стоит, уже есть — служебные
сессии, `checkBudget`, `structuredCall`, гейт облака. Первым агентом делаем
`check-document`: он и так расписан в плане нормоконтроля.

Верификатор получает свой чек-лист от скила, а не общий текст. Общий
`adversary-review` остаётся для чата.

**Как проверяем.** Журнал прогона показывает каждый шаг: какой скил взят,
почему, какой скрипт позван, что вернул. Отказ называет причину. Прогон на
комплекте АВИВАК-2 сходится с ручным разбором.

**Срок.** Три-четыре недели.

### Этап 4. Несколько агентов на один комплект

**Что делаем.** Планировщик разбирает комплект по разделам, исполнители
проверяют каждый своим скилом, сводка собирает находки и снимает дубли.
Дедупликация уже написана в `tz/dedup.js` — переиспользуется.

**Как проверяем.** Полный комплект АВИВАК-2. Число находок и их существенность
сверяются с ручным разбором; расход считается отдельно и объявляется заранее.

**Срок.** По результатам третьего этапа, не раньше.

# Часть VII. Как реализовать — конкретные файлы

| Что | Где | Образец рядом |
|---|---|---|
| Реестр скилов | `server/services/skills.js` (новый) | `services/prompts.js` |
| Папки скилов | `skills/<имя>/SKILL.md` (новая ветка дерева) | `библиотека-промптов/<роль>/` |
| Подбор скила | правка `services/doclib.js` | `classifyByMarkers` там же |
| Исполнитель | `server/services/agents/runtime.js` (новый) | `tz/analyze.js` — три прохода |
| Журнал шагов | колонка в таблицах прогонов | `tz_runs.progress`, журнал нормоконтроля |
| Верификатор со своим чек-листом | правка `claude/adversary.js` | он же |
| Проверка описи | `tests/skills.test.js` (новый) | тест «промты: каждое имя из кода есть файлом» |

Порядок работ обратный привычному: **сначала тест описи, потом папки**. Тест
«у каждого скила есть шапка, и все её ссылки существуют» ловит расхождение
на этапе правки, а не на боевом прогоне.

# Часть VIII. Риски и то, что нельзя сдвигать

| Риск | Чем закрыт |
|---|---|
| Агент возьмёт не тот скил | маркеры кода первыми; выбор человека сильнее; замер на 20 документах до включения |
| Расход вырастет незаметно | бюджет на агента отдельно от бюджета проекта; журнал показывает каждое обращение |
| Локальные данные уедут в облако | `контур: local_only` в шапке скила + гейт `cloud-access.js` на дне адаптера |
| Модель начнёт считать сама | схема шага без варианта «вычислить»; арифметика только скриптом скила |
| Скилы разъедутся с реестром НТД | тест сверяет `источники` шапки с 208 записями реестра |
| Журнал станет неразборчивым | шаг агента пишется теми же словами, что видит человек: «взял скил», «позвал скрипт», «записал находку» |

**Три правила платформы переход не отменяет и не смягчает:**

1. Модель отвечает за интерпретацию и порядок. Координаты, площади,
   пересечения, буферы и реквизиты считает код.
2. У любой находки прослеживается происхождение: из какого документа, какого
   пункта, к какому объекту.
3. Сделано — значит подтверждено настоящими данными и живой моделью. Зелёные
   тесты сделанным не считаются.

# Часть IX. Что решено не делать

- **Не переводить платформу на внешний агентский фреймворк.** Служебные
  сессии, бюджеты, гейт доменов и учёт расхода уже написаны и проверены;
  чужой рантайм пришлось бы обвязывать тем же самым.
- **Не давать агенту право писать в боевые таблицы.** Предложение агента —
  черновик; решение ставит человек, ФИО и дату пишет сервер. Это правило
  датасета и решений по находкам, оно распространяется на агентов без
  исключений.
- **Не сводить несколько прогонов голосованием.** Решение А16-A в силе:
  стабильный промт, `t=0`, фиксированный seed. Скилы этого не меняют.
- **Не переносить в скилы оценку актуальности редакций НТД.** Редакция
  резолвится кодом на момент прогона — правило П46/П53.

## Приложение Г. Что канал предлагает, а платформа решила иначе

- **Сведение двух-трёх прогонов голосованием** в проде не используется:
  решение А16-A — стабильный промт, `t=0`, фиксированный seed. Промты
  сведения остаются в библиотеке для ручной работы.
- **Оценка актуальности редакций моделью** запрещена правилом П46/П53:
  редакция резолвится кодом на момент прогона. Поздний материал канала
  пришёл к тому же выводу самостоятельно.
