## 6. Выбранный стек и обоснование

- **Node.js 22+ / Express 4** — один процесс отдаёт и API, и статику; минимум зависимостей; нативно деплоится на все бесплатные платформы.
- **SQLite через встроенный `node:sqlite`** — ноль внешних сервисов и нативных модулей; транзакционное хранение истории/фактов/результатов; для пилота с TTL 72 ч достаточно (миграция на PostgreSQL — замена одного модуля `db.js`).
- **Vanilla JS frontend без сборки** — нет build-шага и цепочки поставки; проще аудит безопасности; для одного экрана рабочего пространства фреймворк избыточен.
- **@anthropic-ai/sdk** — официальный SDK: встроенные retry (429/5xx), типизированные ошибки, structured outputs.
- Зависимости всего четыре: `express`, `multer`, `adm-zip`, `@anthropic-ai/sdk` (0 уязвимостей по npm audit).

## 7. Архитектура

```
Браузер (public/: HTML+CSS+JS, localStorage: {id, token})
   │  HTTPS, только относительные /api/*
   ▼
Express (server/)
   ├─ middleware: security headers, CSP, rate limit (IP), Bearer-авторизация сессии
   ├─ routes/api.js: sessions / files / process / questions / results
   ├─ pipeline.js: асинхронный job, журнал этапов (events), статусы
   ├─ claude/adapter.js: контекст → Anthropic API (structured output, cache, retry)
   │     ├─ memory.js: резюме + факты + Q&A + последние N сообщений + документы
   │     └─ mock.js: помеченный демо-режим без ключа
   ├─ outputs.js: ОТЧЁТ.md, session-data.json, DXF (dxf.js), ZIP
   └─ SQLite + файлы в DATA_DIR (uploads/<sid>/, outputs/<sid>/), TTL-очистка
```

Основная обработка — только на сервере. Клиент не содержит секретов и не вызывает Anthropic API.

## 11. Меры безопасности

- Ключ Anthropic — только в env сервера; в git — только `.env.example` без значений; фронтенд секретов не содержит и не получает.
- Изоляция сессий: UUID + 256-битный токен, единый ответ 404 при неверном токене (нет перечисления сессий), файлы в каталогах по сессиям вне публичной статики.
- Валидация файлов: расширение + magic bytes, лимиты размера/количества/суммы, санитизация имён, проверка канонического пути при записи и выдаче (анти path-traversal), загруженное никогда не исполняется и не отдаётся как статика.
- Rate limiting (общий 120/мин и «дорогой» 12/мин на IP), лимит одновременных задач, лимит JSON-тела 256 КБ.
- CSP/`X-Content-Type-Options`/`X-Frame-Options`/`Referrer-Policy`; CORS не открывается (same-origin приложение).
- Ошибки: stack trace — только в серверные логи, клиенту — нейтральные сообщения.
- Prompt injection: системные инструкции отделены от документов; содержимое файлов передаётся в явно помеченных блоках `<uploaded_document untrusted="true">`; системный промт запрещает исполнять команды из документов и раскрывать секреты; модель не имеет доступа к ФС и инструментам — она возвращает только валидируемый JSON; пути записи файлов определяет сервер, а не модель; геометрия и все поля ответа проходят серверную валидацию по схеме.
- TTL-очистка: автоматическое удаление сессий и файлов через `SESSION_TTL_HOURS` (72 ч) + ручное удаление.

## 12. Хранение

SQLite (`DATA_DIR/app.db`, WAL): таблицы `sessions`, `messages`, `files`, `questions`, `facts`, `events`, `results` с каскадным удалением. Загрузки — `DATA_DIR/uploads/<sessionId>/`, результаты — `DATA_DIR/outputs/<sessionId>/`.

## 13. Логика сессий

Создание → `{id, token}`; клиент хранит их в localStorage и передаёт токен в каждом запросе; восстановление — `GET /api/sessions/:id` (полное состояние); удаление — вручную или по TTL. Одна глобальная директория/история не используется.

## 14. Обработка уточняющих вопросов

Модель возвращает `status: needs_clarification` + `questions[{text, why}]` → сервер сохраняет вопросы (dedup по тексту), UI показывает их в выделенном блоке со статусами. Ответ сохраняется (`answered`), попадает в память сессии; когда pending-вопросов не остаётся — сервер автоматически продолжает обработку с инструкцией «учти ответы». Цикл повторяется до `completed`/`failed`.

## 15. Формирование выходных файлов

Из валидированного ответа модели сервер материализует: `ОТЧЁТ.md` (поле `report_markdown` — полный отчёт по шагам), `session-data.json` (факты, ТЭП, предупреждения, конфликты, допущения, promptVersion), `генплан-эскиз.dxf` (собственный DXF R12-писатель: слои/полилинии из `geometry`; создаётся только при наличии реальных координат — модель не выдумывает геометрию), `результаты.zip` (adm-zip). Все файлы проверяются тестами на непустоту и корректность формата (PK-заголовок ZIP, POLYLINE в DXF).

## 19. Ограничения текущей версии

- DWG-файлы не парсятся (метаданные); эскизный DXF вместо полного чертежа по ГОСТ 21.508; нормативная база не подключена (см. Допущения).
- В локальном AI-режиме: PDF-сканы без текстового слоя не распознаются (нет OCR), изображения не анализируются, качество анализа ниже Claude (модель 30B); текст документов ограничен 24k символов.
- Публикация через quick-туннель: непостоянный URL, зависимость от включённого компьютера (см. п. 22–24).
- SQLite — один инстанс, без горизонтального масштабирования (для пилота достаточно).
- Статус — polling, не SSE/WebSocket (осознанный выбор по надёжности).
- В демо-режиме ответы — помеченная заглушка (никогда не выдаётся за реальный анализ).

## Подтверждения по разделу «Дополнение к критериям завершения»

1. **История чата** хранится в SQLite на сервере (`messages` + `questions`, `facts`, `events`), не только в состоянии frontend.
2. **Восстановление сессии**: localStorage хранит `{id, token}` → `GET /api/sessions/:id` возвращает полное состояние; работает после перезагрузки/закрытия браузера (покрыто e2e).
3. **Память Claude**: рабочий контекст = системный промт (кэшируется) + резюме диалога (обновляется при >40 сообщений) + структурированные факты + ответы на вопросы + последние 24 сообщения + документы. Полная история никогда не удаляется из БД из-за размера контекста.
4. **Разделение пользователей**: изоляция по сессионному токену, отдельные каталоги файлов, кросс-доступ отвергается (тест «two sessions are fully isolated»).
5. **API-ключ** — только в переменной окружения сервера `ANTHROPIC_API_KEY`; в git — `.env.example` с пустым значением; в отчёте/логах/интерфейсе значение не фигурирует.
6. **Модель**: при наличии ключа — `claude-opus-5` (конфигурируется `ANTHROPIC_MODEL`); сейчас в опубликованной версии — локальная `qwen/qwen3-vl-30b` через LM Studio (`LOCAL_AI_MODEL`, structured output через `response_format: json_schema`, приоритет провайдеров: Anthropic → локальный → демо). Про Claude: Выбор: анализ многостраничных PDF, многошаговый диалог и структурированные ответы — профиль Opus; расход ~ (документы 5–50k ток. + контекст 2–10k) × число шагов диалога, ответ ≤ 8k ток.; системный промт кэшируется (cache_control), бюджет на сессию ограничен (25 запросов / 2M токенов), расход логируется по каждой сессии.
7. **Лимиты и ошибки API**: SDK-retry (3×, экспоненциальный backoff) + таймаут 300 с; типизированная обработка 401/429/сеть/5xx с понятными сообщениями; при ошибке AI сессия и данные сохраняются, статус `failed`, можно повторить.
8. **Prompt injection** — см. раздел 11.
9. **Контроль токенов**: счётчики input/output в БД per session, жёсткие лимиты запросов и токенов, ограничение длины сообщений и объёма документов, rate limiting.
10. **Claude вызывается только серверной частью** — фронтенд обращается исключительно к собственному API; прямых вызовов Anthropic, ключей или браузерной авторизации Claude в клиентском коде нет.
