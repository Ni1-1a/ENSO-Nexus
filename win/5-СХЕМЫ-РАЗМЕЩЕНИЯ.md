# 5. Где что стоит: сервер на Windows, тяжёлая модель на маке

Выбранный расклад:

- **Windows** — сервер платформы, база `data/`, туннель наружу. Машина слабая,
  на ней стоит LM Studio с небольшой моделью.
- **Мак** — LM Studio с рабочей моделью (`qwen3.5-35b-a3b`), vision-модель для
  сканов и модель эмбеддингов. Сервер обращается к ней по сети.
- **База знаний** лежит в стороне от проекта, путь задаётся отдельно.

Работает без правок кода: к локальной модели платформа ходит по HTTP, адрес —
одна переменная. Проверено по коду: через `LOCAL_AI_BASE_URL` идут **все**
обращения к LM Studio — анализ и чат (`claude/adapter.js:253`), распознавание
сканов (`doc-vision.js:176`), эмбеддинги базы знаний (`kb.js:174`), список
моделей в интерфейсе (`providers.js:85`) и проба при старте (`index.js:9`).

Одна правка всё же обязательна — из-за того, что LM Studio будет и на Windows.
Она в п. 3.

---

## 1. Что настроить на маке

1. LM Studio → сервер разработчика → включить **Serve on Local Network**.
   По умолчанию она слушает только `127.0.0.1`, и с Windows её не видно.
2. Разрешить входящие на 1234 в брандмауэре macOS.
3. Узнать адрес мака в локальной сети и закрепить его за ним в роутере
   (DHCP-резерв) — иначе после перезагрузки роутера платформа «потеряет модель»:

   ```bash
   ipconfig getifaddr en0
   ```

4. Сон выключить: считает теперь мак. Крышку не закрывать либо держать рядом
   `caffeinate -i`.
5. **Загрузить три модели и задать им контексты прямо в LM Studio** — почему это
   теперь делается руками, объяснено в п. 3:

   | модель | зачем | контекст |
   |---|---|---|
   | `qwen/qwen3.5-35b-a3b` | анализ, извлечение ограничений, чат | 32 768 |
   | `qwen/qwen3-vl-8b` | распознавание сканов (17 страниц ГПЗУ) | 16 384 |
   | `text-embedding-qwen3-embedding-0.6b` | поиск по базе знаний | по умолчанию |

   Числа занижены против нынешних `98304/65536` намеренно: раньше сервер грузил
   модели **по одной** (`LOCAL_AI_EXCLUSIVE=1`) и каждой доставался весь бюджет
   памяти. Теперь выгружать соседа некому, и все три обязаны помещаться
   одновременно: 20,6 ГБ весов чат-модели + 5,4 ГБ vision + KV-кэши. Подбирать
   замером (см. [4-ЧЕКЛИСТ.md](4-ЧЕКЛИСТ.md), п. 7), а не на глаз.

## 2. Что прописать на Windows, в `.env`

```ini
AI_PROVIDER=local

# ГЛАВНЫЙ адрес — мак. Сюда жёстко ходят: анализ, распознавание сканов
# и эмбеддинги базы знаний. Значит vision-модель и модель эмбеддингов
# обязаны быть именно на маке.
LOCAL_AI_BASE_URL=http://192.168.1.50:1234/v1
LOCAL_AI_MODEL=qwen/qwen3.5-35b-a3b
LOCAL_AI_OCR_MODEL=qwen/qwen3-vl-8b
LOCAL_AI_CONTEXT=32768        # ровно то, что выставлено в LM Studio на маке
LOCAL_AI_OCR_CONTEXT=16384
LOCAL_AI_TIMEOUT=600000

# Слабая LM Studio на самой Windows — отдельным провайдером в интерфейсе.
# Запасной путь на случай, когда мак выключен.
OLLAMA_BASE_URL=http://localhost:1234/v1

ACAD_ENABLED=0
```

Про слот `ollama`: в коде это полноценный второй OpenAI-совместимый маршрут со
своим адресом (`adapter.js:257`, `providers.js:85`), а LM Studio отдаёт как раз
OpenAI-совместимый API — то есть местная LM Studio появится в пикере моделей
рядом с маковской. Две оговорки:

- в интерфейсе слот подписан **«Ollama (локально)»** (`providers.js`) — метка
  правится одной строкой там же, если надпись будет путать;
- по реестру возможностей у слота `ollama` нет ни зрения, ни эмбеддингов
  (`ai/registry.js:86`) — сканы и поиск по базе знаний через него не пойдут
  в любом случае. Это ровно то, чего от слабой машины и не ждут.

Проверка связи с Windows:

```powershell
curl.exe -s http://192.168.1.50:1234/v1/models
```

## 3. Обязательная правка: менеджер моделей не должен трогать чужую LM Studio

`server/services/model-manager.js` управляет моделями через **локальный** CLI
`lms`: грузит с нужным контекстом, выгружает соседа, считает бюджет памяти от
`os.totalmem()`. По сети он не работает.

Пока LM Studio на Windows нет, всё разрешается само: `findLms()` вернёт `null`,
`ensureLoaded()` честно отдаст `{ok:true, managed:false}` («нет CLI — надеемся
на JIT»), и платформа положится на автозагрузку самой LM Studio. Но в вашем
случае LM Studio на Windows **будет**, вместе с CLI. Тогда получается худшее:
менеджер начнёт грузить и выгружать модели на слабой машине, пока запросы уходят
на мак, а в интерфейсе рабочая 35B-модель отметится как «не помещается в память»
— бюджет-то посчитан по оперативке Windows.

Правка в три строки. В `model-manager.js`, сразу после `LMS_CANDIDATES`:

```js
/*
 * Управлять моделями можно только там, где они работают. Если LM Studio вынесена
 * на другую машину (LOCAL_AI_BASE_URL смотрит не в петлю), локальный CLI управлял
 * бы ЧУЖОЙ, не той LM Studio: грузил бы модели на этой машине, пока запросы уходят
 * на соседнюю. В таком случае менеджер обязан молчать — загрузку берёт на себя
 * сама LM Studio (JIT), а контекст задаётся в её настройках.
 */
const REMOTE_LM = !/^https?:\/\/(localhost|127\.0\.0\.1|\[::1\])(:|\/)/i
  .test(config.localAiBaseUrl);
```

и первой строкой в `findLms()`:

```js
function findLms() {
  if (REMOTE_LM) return null;
  // …дальше как было
```

Что из-за этого пропадает (и это надо принять сознательно):

- **загрузка с заданным контекстом** — контекст теперь задаётся в LM Studio на маке;
- **поочерёдная работа моделей** (`LOCAL_AI_EXCLUSIVE=1`) — выгружать соседа
  некому, поэтому все три модели должны помещаться разом (п. 1.5);
- **подсказки «модель не помещается / влезет с окном N»** в пикере — там, где
  менеджер молчит, `providers.js` показывает модели без этих оценок.

Взамен исчезает риск, ради которого правка и делается: сервер больше не трогает
модели на машине, которая ими не занимается.

## 4. Что перестаёт работать в этой схеме

| | |
|---|---|
| **Мост AutoCAD** | и так только macOS: он ходит в AutoCAD через папку обмена и AppleScript **на машине сервера**, а сервер теперь Windows. `ACAD_ENABLED=0`, DWG собирает конвертер LibreDWG с пометкой «(конвертер)» |
| **Мак выключен** | пропадает анализ, распознавание сканов и поиск по базе знаний (эмбеддинги считает мак). Платформа, вход, прошлые проекты и чертежи — работают; в пикере остаётся слабая местная модель и облако |
| **Картинки сканов идут по сети** | страница PDF при 150 dpi — 0,5–2 МБ; на 17 страницах по локальной сети это незаметно, через интернет — уже нет. Машины должны быть в одной сети |

## 5. База знаний «в другом месте»

Здесь важно различать две вещи, которые легко спутать.

**Индекс живёт в базе проекта, а не в папке.** Чанки и эмбеддинги лежат в таблице
`kb_chunks` внутри `data/app.db` (12,5 тыс. чанков). Поиск читает только её
(`kb.js:264` — один SQL, никакого обращения к диску). Значит: перенесли `data/`
— поиск по базе знаний работает **сразу**, даже если самой папки на Windows ещё
нет.

**Папка нужна только для переиндексации** — `npm run kb:index` читает из неё
`09_Векторный-индекс/` и `04_JSON/` (`kb.js:38-41`).

Отсюда правила:

```ini
KB_DIR=D:\Базы\Knowledge-Base          # или \\MAC\Knowledge-Base, или любой другой путь
```

1. **`KB_DIR` обязана быть непустой** — из неё собирается список баз
   (`config.js`: `kbBases`), а от него зависят и отметка «база подключена» в
   `/api/health`, и выбор базы в проекте (`api.js:733`). Пустая переменная = базы
   знаний в интерфейсе нет вообще, даже при полном индексе в SQLite.
2. **Не запускайте `npm run kb:index`, если папка недоступна.** `reindex()`
   сначала делает `DELETE FROM kb_chunks`, и только потом читает диск
   (`kb.js:193-199`): при отвалившемся сетевом диске или размонтированном томе
   получится «0 чанков» и уничтоженный индекс. Восстанавливать — из копии `data/`.
3. **Эмбеддинги при переиндексации считает мак** (запрос уходит на
   `LOCAL_AI_BASE_URL`), поэтому индексировать можно только при живом маке
   с загруженной моделью эмбеддингов.
4. **База Гриши выводится из `KB_DIR` соседней папкой** (`Knowledge-Base-Гриша`
   рядом), а её состав — из `<KB_DIR>\07_Заметки\Коллекции\НТД_Гриша.md`. Если
   раскладка другая, задайте явно:

   ```ini
   KB_GRISHA_DIR=D:\Базы\Knowledge-Base-Гриша
   KB_GRISHA_COLLECTION=D:\Базы\Knowledge-Base\07_Заметки\Коллекции\НТД_Гриша.md
   ```

5. **Если папка остаётся на маке** — путь писать сетевой, UNC-именем
   (`\\MAC\Knowledge-Base`), а не буквой подключённого диска: буквы существуют
   только внутри сеанса пользователя, и служба или задача планировщика их не
   видит. Плюс общий доступ на маке (Системные настройки → Общий доступ →
   Общий доступ к файлам) и постоянный адрес.

Итог для переноса: папку `Knowledge-Base` (673 МБ) можно **не тащить сразу** —
достаточно `data/`. Она понадобится, когда базу придётся переиндексировать.

## 6. Альтернатива, если мак всё равно всегда включён

Раз тяжёлое считает мак и без него платформа наполовину бесполезна, можно не
переносить приложение вовсе, а вынести на Windows **только туннель**: на маке
всё остаётся ровно как сегодня (менеджер моделей, мост AutoCAD, `data/`,
привычные `.command`-файлы), а Windows работает сетевым выходом.

- на маке в `.env`: `BIND_HOST=0.0.0.0` и `TRUST_PROXY=<ip-винды>`
  (второе обязательно: по умолчанию стоит `loopback`, и без него все посетители
  сольются в один адрес — общий лимит попыток входа станет один на всех;
  ставить `1` или «верить всем» нельзя, на `0.0.0.0` заголовок подделывается
  с любой машины в сети);
- запускать на маке **без своего туннеля**: `caffeinate -i npm start`;
- на Windows — только `cloudflared`, в ingress `service: http://<ip-мака>:3000`.

Плата: адрес мака в локальной сети должен быть постоянным, и обе машины
включены — но это условие и так выполняется в выбранной схеме.
